# Привязка готовых сборок к прайс-листам

## Цель

Продавец формирует «Готовые конфигурации» в отдельном разделе своего профиля,
собирая их из своего прайс-листа в инструменте, аналогичном Конфигуратору.
В сборку попадают только активные позиции активного прайса с ненулевой ценой.
Название сборки = «Бренд» (из справочника брендов Продавца `seller_brand`) + введённая модель.

Готовые сборки сохраняют постоянную связь с прайс-листом. Сборка считается
**невалидной**, если хотя бы один её компонент в активном прайсе Продавца
отсутствует / деактивирован / имеет нулевую цену. Невалидная сборка:
недоступна на странице готовых сборок и в карточке; у Клиента в сохранённых
сборках помечается недоступной к заказу. Если невалидная (на момент оценки)
сборка попала в Заказ Клиента, в заказе она остаётся как была (снимок).

## Принятые решения (подтверждены пользователем)

- **Хранение:** переиспользуем таблицу `ready_pc` (`seller_id`, `name`, `brand`,
  `ready_pc_part`). Существующие seeded-сборки Confi (`usr-seller`) — это те же
  «готовые сборки» Продавца, их не выделяем особым флагом.
- **Валидность:** вычисляется на лету при чтении по активному прайсу продавца
  (без новых колонок и триггеров; как текущая живая переоценка).
- **UI:** новая вкладка «Готовые конфигурации» в профиле продавца (и админа);
  создание/редактирование через переиспользованный `ComponentPicker` с выбором
  только активных позиций ненулевой цены активного прайса.
- **Права:** владелец-продавец или `admin` (как у `priceListsActor`/`sellerBrandActor`).
- **Область валидности:** страница готовых ПК + карточка `PcCard` + сохранённые
  конфигурации клиента `source=ready`. Заказы (снимок в `order_item`) не трогаем.
- **Копирование в конфигуратор** (`Настроить в конфигураторе`/`Открыть в
  конфигураторе`) разрешено и для невалидных сборок.
- **Мягкое удаление (архив).** Продавец может деактивировать готовую сборку
  (`is_active=0`) — она исчезает из витрины и перестаёт связывается с прайсом, но
  остаётся в архиве и может быть восстановлена (`is_active=1`). Повторяет паттерн
  деактивации/реактивации компонентов.
- **Уникальность модели.** Поле «Модель» уникально среди **активных** сборок
  одного продавца (регистронезависимо). Бренд в проверку не входит — уникальность
  именно модели. Архивные сборки не резервируют модель (при восстановлении модель
  пересчитывается заново).

## Терминология в коде

- «торговая марка» компонента = `vendor` (Intel/AMD/Confi…);
- «бренд продавца» = запись `seller_brand.brand` (напр. `Confi`);
- «модель сборки» = новый вводимый суффикс, например `Gaming 1440p`.
- Полное название готовой сборки = `Бренд + « » + модель` (кладём бренд в
  `ready_pc.brand`, модель — в `ready_pc.name` как суффикс или в отдельное поле).

### Решение по полю `name` (модель + бренд)

Сейчас `ready_pc.name` хранит полное имя («Confi Office 3000»), `ready_pc.brand` —
бренд («Confi»). Чтобы не ломать существующие данные и каталог:
- `ready_pc.brand` = выбранный бренд продавца (из `seller_brand`).
- `ready_pc.name` = полная строка вида `Конфигурация <Бренд> <модель>` ИЛИ просто
  «Конфигурация <модель>». Формирование на сервере композицией, как `composePartName`.

> Итоговое правило (по ответу пользователя «Бренд + введённая модель»):
> `name = composeBuildName(brand, model)` = `brand + " " + model`.
> Модель не хранится отдельной колонкой — восстанавливается как
> `model = stripPrefix(name, brand)` при редактировании (см. `modelFromName`).

Предпочтение: **НЕ вводить новую колонку** — при создании/редактировании сервер
принимает `{ brand, model }`, вычисляет `name = composeBuildName(brand, model)` и
сохраняет; при открытии формы редактирования клиент восстанавливает `model` через
`stripPrefix(name, brand)`. Соответствует текущему паттерну компонентов.

> **Уникальность модели на уровне данных.** Уникальность не выражается схемой
> (`ready_pc` без UNIQUE по модели, а модель не хранится отдельной колонкой),
> поэтому проверяется в транзакции на сервере при `POST`/`PUT`/восстановлении:
> `SELECT count(*) FROM ready_pc WHERE seller_id=? AND is_active=1 COLLATE NOCASE
> AND name=?` (для `PUT`/reactivate — исключая саму сборку по `ready_pc_id`).
> Конфликт → `409 model_exists`.

## Дизайн данных

Новые API используют существующие таблицы, **без миграции схемы**:

- Чтение `ready_pc` уже возвращает `parts` (живые цены из активного прайса через
  `readyPcWithParts`). Добавляем вычисляемый флаг `valid`.
- `seller_brand` — источник выбора «Бренд» в форме сборки.
- Активный прайс продавца = `price_list WHERE seller_id=? AND is_active=1`.

## Изменения по слоям

### 1. Серверный DAO — `src/server/repository/catalog.ts`

- В `ReadyPcDto` (в `types.ts`) добавить `valid: boolean` и (для удобства UI
  продавца) `sellerId: string | null`.
- В `readyPcWithParts` вычислить `valid`:

  - каждая категория имеет `part` (не null) и `part.available === true`

  - завершить через `isPartOrderable(part)` (см. п.2); при подсчёте состава

- Добавить DAO-метод формирования имени не нужен (серверный хелпер в `index.ts`).
- `listReadyPcs`/`getReadyPc` возвращают `valid` и фильтруют `is_active=1`
  (архивные не попадают в публичный каталог; для списка продавца

- Добавить DAO-методы мягкого удаления/восстановления готовой сборки:
  `deactivateReadyPc(id)` (`is_active=0`) и `reactivateReadyPc(id)` (`is_active=1`).
- Проверка уникальности модели — в отдельном DAO-методе
  `readyModelExists(sellerId, name, excludeId?)`.

### 2. Клиентский хелпер валидности

- `src/lib/compatibility.ts`: добавить `isBuildCompleteValid(parts: ConfigPart[]): boolean` =
  `parts.length === 8 && parts.every(cp => !!cp.part && isPartAvailable(cp.part))`.
  Использовать на клиенте для локальной проверки при сборке, а `valid` с сервера —

### 3. Серверные маршруты — `src/server/index.ts`

Добавить `readyBuildsActor` (по образцу `priceListActor`): `actorRole` + владелец
(`actor.userId === :id`) или `admin`.

- `GET /api/seller/:id/ready` — список готовых сборок продавца с `valid`,
  `sellerId`, `brand`, `name`, состав. (Владелец или admin.)
- `GET /api/seller/:id/ready/:buildId` — одна сборка (для редактирования).
- `POST /api/seller/:id/ready` — создать. Тело: `{ brand, model, parts: PartRef[] }`,
  где `PartRef = { category, partId }`. Сервер:
  - `brand` должен существовать в `seller_brand` этого продавца;
  - `name = composeBuildName(brand, model)`;
  - вычисляет `tdp_watt` из частей, `price_kopecks` = сумма цен активного прайса
    (дополнительно, для согласованности с витриной), `summary`/`specs` — авто или
    заполняются простыми значениями; `is_active=1`, `in_stock=1`, `rating=5`;
  - вставляет `ready_pc` + `ready_pc_part` (в транзакции).
- `PUT /api/seller/:id/ready/:buildId` — перезапись состава/модели/бренда.
- `DELETE /api/seller/:id/ready/:buildId` — **мягкое удаление** (`is_active=0`, в архив).
- `POST /api/seller/:id/ready/:buildId/reactivate` — восстановление из архива (`is_active=1`).
- Валидация состава: все 8 категорий заполнены активными позициями с ценой >0 из
  активного прайса продавца (иначе `400 invalid_build`).
- **Уникальность модели** в транзакции (`409 model_exists`): при `POST`, `PUT` и
  `reactivate` — модель должна быть уникальной среди **активных** сборок продавца
  (регистронезависимо, исключая текущую сборку при обновлении/восстановлении).

Публичные маршруты готовых ПК:
- `GET /api/ready?valid=1` (новый опциональный query) — возвращает только валидные
  сборки выбранного продавца. Без `valid` — как сейчас (чтобы не ломать другие вызовы).
- `GET /api/ready/:id` — возвращать `valid` в теле; `PcCard` на клиенте решает,
  показывать ли «недоступна к заказу».

### 6. Переиспользование ComponentPicker для продавца

`ComponentPicker` сейчас грузит `fetchParts(category, undefined, sellerId)` — это
уже активные позиции (`is_active=1`), и блокирует без цены (`noPrice`). Для сборок
продавца это почти готово. Достаточно:
- передавать `sellerId` продавца;
- убрать/не требовать проверку совместимости при постройке (или переиспользовать
  — предпочтительно оставить живую проверку, как в конфигураторе, т.к. сборка
  должна быть собираемой);
- блокировать выбор деактивированных и нулевых цен (уже есть в `noPrice`).

Рекомендация: переиспользовать `ComponentPicker` как есть с `sellerId`, при этом
сборка фиксируется по факту выбора во все 8 слотов.

### 8. Сохранённые сборки клиента `source=ready`

`user-data.ts configPartsFor` уже обрабатывает `source === "ready"` живьём: слот с
`current<=0`/часть недоступна → `part: null, unavailableReason`. Это уже помечает
позиции недоступными. Добавить на уровне `Config` признак валидности готовой
сборки, чтобы в профиле показать бейдж «Сборка недоступна к заказу»:
- в `ConfigDto`/`Config` (клиент) добавить `buildInvalid?: boolean` (только для
  `source=ready`), сервер вычисляет `configPartsFor` → если любой слот `part===null`
  → `buildInvalid=true`.
- `Profile.tsx` (вкладка «Конфигурации»): для `c.source==='ready' && c.buildInvalid`
  показывать бейдж «Сборка недоступна для заказа»; кнопки «Открыть в конфигураторе»
  и «Удалить» сохранить.

### 9. Архив (мягкое удаление) и восстановление — сервер

- `DELETE /api/seller/:id/ready/:buildId` — мягкое удаление: `is_active=0`.
  Сборка остаётся в БД (состав, отзывы, история заказов не затронуты), исчезает
  из витрины и из списка активных сборок продавца. Идемпотентно: повторный
  `DELETE` по уже деактивированной — `200/204` без ошибки.
- `POST /api/seller/:id/ready/:buildId/reactivate` — восстановление из архива:
  `is_active=1`. Перед активацией проверить уникальность модели среди активных
  сборок продавца → конфликт `409 model_exists`.
- Удалённая из каталога часть / обнулённая цена уже обрабатываются проверкой
  валидности на чтение, т.е. после восстановления сборка пересчитывается по
  актуальному прайсу и может оказаться невалидной (показывается как невалидная,
  а не блокируется) — согласовано с «постоянной связью с прайсом».

## Область валидности (итог)

| Место | Поведение при невалидной сборке |
| --- | --- |
| Страница `/ready` | Сборка скрыта (`GET /api/ready?valid=1`, макс. `is_active=1`) |
| Карточка `/ready/:id` | Бейдж «Недоступен к заказу», скрыты заказ/рассрочка |
| Сохранённая конфигурация клиента `source=ready` | Бейдж «Сборка недоступна к заказу», позиции показывают «недоступен» |
| Заказ клиента | Без изменений (снимок) |
| «Настроить в конфигураторе» | Разрешено |
| Архив продавца (деактивированные) | Видны только продавцу/admin в архиве; «Восстановить» |

## Риски и открытые вопросы

1. **Мягкое удаление.** `is_active=0` сохраняет состав, отзывы и историю заказов
   (в отличие от физического `DELETE`, который каскадно удалил бы `ready_pc_part`
   и `review`). Восстановление — `is_active=1`. Архивные сборки невидимы на
   витрине (`GET /api/ready?valid=1` дополнительно фильтрует `is_active=1`).
2. **`composeBuildName`/суффикс модели.** Подтверждено: `name = brand + " " + model`.
   При редактировании модель восстанавливается `stripPrefix(name, brand)`. Если у
   старого seeded-имени префикс не совпадает с `brand`, форма покажет весь `name`
   как модель без бренда (partially корректно; приемлемо для задачи). Уникальность
   проверяется по полному `name` активной сборки.
3. **Цена/`price_kopecks` готовой.** Витрина пересчитывает из `parts`, поэтому
   хранимое `ready_pc.price_kopecks` используется редко, но заполняем для консистентности.
4. **`GET /api/ready?valid=1`** — обратная совместимость: по умолчанию без флага
   возвращаем всё как сейчас (не ломаем автотесты и другие вызовы). Дополнительно
   фильтрует `is_active=1` (архивные скрыты).
5. **Уникальность только среди активных.** Если сборка в архиве несёт занятую
   модель, новая активная может занять то же имя; при восстановлении архивной из-за
   конфликта будет `409` — ожидаемое поведение.

## Тесты

- Юнит (`src/lib/compatibility.ts`): `isBuildCompleteValid` — все 8 слотов валидны /
  один слот недоступен / часть отсутствует / цена 0.
- Серверный E2E (`tests/`): создание готовой сборки продавцом; `403` для клиента;
  деактивация компонента в каталоге → сборка становится невалидной и скрывается с
  `/ready` при `?valid=1`; обнуление цены в активном прайсе → та же сборка
  невалидна; удаление бренда → и т.п.
- **Архив:** мягкое удаление → сборка исчезает с витрины и из активного списка
  продавца, появляется в архиве; восстановление → снова видна и валидна по прайсу.
- **Уникальность модели:** создание/обновление/восстановление с занятой моделью
  активной сборки → `409 model_exists`; модель, занятая только архивной сборкой,
  может быть взята новой активной.
- Регрессия витрины: существующие сборки Confi по-прежнему видны и карточка работает
  (сед уже валиден: все 8 категорий есть, прайс «Основной» с ценами >0).
- Checkout/рассрочка для валидной сборки не сломаны.
