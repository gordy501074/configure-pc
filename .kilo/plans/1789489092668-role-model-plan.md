# Ролевая модель Confi (Гость / Клиент / Продавец / Администратор)

## Цель

Ввести в приложение Confi четыре роли с разграничением доступа:

- **Гость** — аноним без профиля: просматривает публичные страницы, работает с конфигуратором и автоподбором (без сохранения). Профиль, оформление заказов и админка закрыты.
- **Клиент** — текущий функционал залогиненного пользователя (профиль, сохранение сборок, заказы, отзывы, настройки). Покупатель готовых и кастомных конфигураций. Профиль содержит email и телефон; вход — по email или по телефону (SMS).
- **Продавец** — пользователь с профилем; связь Продавец ↔ Бренды (1-к-многим). Профиль продавца получает раздел-плейсхолдер «Прайс-лист (в разработке)». Бренд **Confi** закрепляется за **user@company.com**. В профиле **нет телефона**, вход — только по email. Самообслуживание: редактирует имя и поле «Компания». Сам прайс-лист и Справочник компонентов — отдельная задача.
- **Администратор** — управление пользователями: список, создание/удаление, назначение роли (customer/seller/admin). Роль закрепляется за **avgordeev@alfabank.ru**. В профиле **нет телефона**, вход — только по email.

Продавцов и Клиентов может быть **несколько**. Клиент и Продавец могут **изменять имя своего аккаунта**; в профиле Продавца есть поле **«Компания»**, которое он также редактирует.

## Принятые решения

- **Гость = аноним** без `user_account`/`auth_session`. Роль `'guest'` убирается из enum пользователей; в админке роли «Гость» нет. Кнопка «Войти как гость» превращается в «Продолжить без аккаунта» (анонимный просмотр, сессия не создаётся).
- Контроль доступа — **клиентские UI-гейты + серверные проверки ролей** для чувствительных операций (администрирование, бренды продавца) на основе сессии.
- UI Продавца — минимальный плейсхолдер «Прайс-лист — в разработке».
- Вход по e-mail восстанавливает роль существующего пользователя из БД (не жёсткое `customer`).
- **Аутентификация по роли**: Клиент имеет и email, и телефон — входит любым способом (email или SMS). Администратор и Продавец в профиле **не имеют телефона** и входят **только по email**.
- Администрирование — **отдельный роут `/admin`** для роли `admin`.
- Связь Продавец↔Бренд — **таблица `seller_brand`** (1-к-многим).
- Миграция схемы — идемпотентный **rebuild `user_account`** из-за изменения CHECK (SQLite не меняет CHECK на лету), версия БД → `3`.
- Продавцов и Клиентов может быть **несколько** (модель уже 1-к-многим по `user_account`).
- Клиент и Продавец **редактируют имя** аккаунта; Продавец дополнительно редактирует поле **«Компания»** (`company`). Самообслуживание — через собственный профиль (`PATCH /api/profile`), без участия админа.

## Текущее состояние

- `user_account.role` типа `'customer' | 'guest'` с CHECK; гостю создаётся строка и сессия.
- Вход по email/телефону всегда создаёт `customer`; «Войти как гость» создаёт `guest`.
- Данные в SQLite через Express; доступ к `/api/configs`, `/api/orders` и др. — по `?userId=` без серверных проверок ролей.
- В UI роли только `customer`/`guest` (бейдж в `Profile.tsx`, ссылка на профиль в `Navbar.tsx`).
- Нет миграционного фреймворка: `db/init.js` переприменяет `db/schema.sql` (`CREATE TABLE IF NOT EXISTS`, `PRAGMA user_version` статична). Для существующей БД `schema.sql` не меняет CHECK.

## Scope / ограничения

- НЕ реализуются: прайс-лист продавца, Справочник компонентов, выбор компонентов в прайс-листе. Только связь Продавец↔Бренды и чтение брендов.
- Гость не имеет профиля: `/profile`, `/profile/*`, `/checkout`, `/alpha`, `/admin` недоступны анониму.

## Схема и данные

### `db/schema.sql` (источник новых DDL; применяется к новым БД)
- Изменить CHECK роли:
  ```sql
  role TEXT NOT NULL DEFAULT 'customer' CHECK (role IN ('customer','seller','admin'))
  ```
- Добавить колонку `company` в `user_account` (поле «Компания» продавца, `NULL` для клиентов):
  ```sql
  company TEXT
  ```
- Добавить таблицу `seller_brand`:
  ```sql
  CREATE TABLE IF NOT EXISTS seller_brand (
    seller_id TEXT NOT NULL,
    brand     TEXT NOT NULL,
    PRIMARY KEY (seller_id, brand),
    FOREIGN KEY (seller_id) REFERENCES user_account(user_id) ON DELETE CASCADE
  ) STRICT, WITHOUT ROWID;
  ```
- Поднять `PRAGMA user_version = 3;`.

### `db/init.js` — идемпотентная миграция (rebuild user_account)
Выполнять ПОСЛЕ применения `schema.sql`, в каждой попытке (безопасно повторно):

1. Ограничение: если `sqlite_master` для `user_account` уже содержит `'seller'` в DDL_CHECK — миграция уже выполнена, пропустить (проверка по `PRAGMA table_info`/`sqlite_master.sql` на вхождение `'admin'`).
2. Отключить FK: `PRAGMA foreign_keys = OFF; PRAGMA defer_foreign_keys = ON;` — внутри одной транзакции.
3. Пересоздать `user_account` с новым CHECK **и колонкой `company`** (копия DDL, без `'guest'`):
   - `ALTER TABLE user_account RENAME TO user_account_old;`
   - создать `user_account` с новым CHECK + `company TEXT`;
   - `INSERT INTO user_account (user_id, name, email, phone, role, company, created_at) SELECT ..., company, created_at FROM user_account_old WHERE role <> 'guest';` (гостевые строки отбрасываются — демо);
   - `DROP TABLE user_account_old;`
4. Пересоздать FK-индексы/связи, если были привязаны к имени таблицы — внешние ключи пересоздаются автоматически для новых имён; пересоздать индексы `idx_user_acct_*` (если такие есть) по нуждам.
5. `PRAGMA foreign_key_check;` — убедиться в целостности; `PRAGMA foreign_keys = ON;`.
6. `PRAGMA user_version = 3;` (в конце, в транзакции).

> Примечание: `db/seed.js` также применяет `schema.sql` перед сидом — проверить, что он вызывает ту же миграцию (лучше вынести миграцию в общую функцию `db/migrate.js` и вызывать из `init.js` и `seed.js`), чтобы сид с ролью `seller` не упал на старом CHECK.

### Seed (`db/seed.js`) и тест-сид (`tests/helpers/testDb.ts`)
Добавить предсозданных пользователей и бренд (идемпотентно):

```sql
INSERT INTO user_account (user_id, name, email, phone, role, company) VALUES
  ('usr-admin',  'Администратор', 'avgordeev@alfabank.ru', NULL, 'admin', NULL),
  ('usr-seller', 'Продавец Confi', 'user@company.com', NULL, 'seller', 'Confi Маркет')
ON CONFLICT(user_id) DO UPDATE SET email=excluded.email, phone=NULL, role=excluded.role, company=excluded.company;
INSERT INTO seller_brand (seller_id, brand) VALUES ('usr-seller', 'Confi')
ON CONFLICT(seller_id, brand) DO NOTHING;
```
- Админ и продавец сидятся с `phone = NULL` (нет телефона). У продавца задаётся `company` (пример «Confi Маркет»).
- В `testDb.ts` повторить те же INSERT.
- `db/verify.js` — count по `user_account`/`seller_brand`.

> Важно: seed очищает `user_account` (`DELETE FROM user_account`) в транзакции и заново вставляет каталог. Продавец/админ должны вставляться ПОСЛЕ `DELETE`, а `seller_brand` — только после создания соответствующего `user_account` (FK).

## Серверная часть

### Типы (`src/server/repository/types.ts`)
- `UserRole = "customer" | "seller" | "admin"` (убрать `"guest"`).
- Добавить `company?: string` в `UserRow` и `UserDto`. При необходимости `SellerBrandDto { brand: string }`.
- `upsertUser`/`userToDto`/`createUser` — учитывать `company`.

### DAO `seller_brand` (`src/server/repository/seller.ts`, новый)
- `listSellerBrands(sellerId): string[]`.

### `src/server/repository/user-data.ts`
> Критично: сейчас `upsertUser` генерирует новый `user_id`, если `id` не передан, а клиентское `Auth.tsx` при входе `id` не передаёт → каждый вход создаёт новую запись. Без правки «вернуть роль по email» невозможно. Нужно добавить поиск существующего пользователя.

- `upsertUser` — новая логика поиска и восстановления: 
  1. Если передан `id` — найти по `id`.
  2. Иначе, если передан `email` — найти по `email`.
  3. Иначе, если передан `phone` — найти по `phone`.
  4. Если такой пользователь найден — **переиспользовать его `user_id` и его текущую роль** из БД (запрашиваемая роль ИГНОРИРУЕТСЯ), обновить `name`/контакты, вернуть тот же аккаунт (данные клиента — сборки/заказы — сохраняются).
  5. Если не найден — создать с ролью `customer` (новый клиент).
- Это делает стабильным вход по email для админа/продавца (возврат роли) и по email/телефону для клиента (стабильный аккаунт).
- Перевод роли не через `upsertUser`, а только через админ-метод `setUserRole`.
- **Ограничение аутентификации по роли** (в `upsertUser`/`POST /api/session`):
  - Клиент — может входить по телефону или email; имеет оба поля.
  - Админ/Продавец — **вход только по email**; телефон в профиле отсутствует (`phone = NULL`). SMS-вход для них отклоняется (либо не отображается в UI, либо на сервере отклоняется при известном email/role).
- **Самообслуживание профиля** (для Клиента и Продавца) — новый метод `updateProfile(userId, patch)`:
  - Клиент и Продавец могут изменять `name`.
  - Продавец дополнительно может изменять `company` («Компания»).
  - Роль через этот метод меняться не может; клиент не может ставить `company` (только продавец).
- Новые методы для админа:
  - `listUsers(): UserDto[]`
  - `createUser({name, email?, phone?, role, company?}): UserDto`
  - `deleteUser(id): boolean`
  - `setUserRole(id, role): UserDto`
- Роль уже возвращается в `user.role`.

### API-роуты (`src/server/index.ts`)
- `POST /api/session`: валидировать `role` — только `customer|seller|admin` (нет `guest`); благодаря новому `upsertUser` при известном `email`/`phone`/`id` восстанавливается существующая запись и её роль из БД.
- Новый (самообслуживание, авторизованный):
  - `PATCH /api/profile` — обновить `name` (клиент/продавец) и `company` (продавец); требует сессии, роль определяется из неё и не меняется.
- Новые (admin, серверный guard):
  - `GET /api/users` — список
  - `POST /api/users` — создать
  - `DELETE /api/users/:id` — удалить
  - `PATCH /api/users/:id/role` — назначить роль
- Новый (продавец или admin):
  - `GET /api/seller/:id/brands` — бренды продавца (владелец или admin).

### Серверная проверка ролей
- Нужен парсер куки `confi_session`: добавить лёгкое чтение вручную из заголовка `Cookie` (зависимость `cookie-parser` не обязательна; допустимо вручную распарсить `confi_session=...`). Резерв — `body.sessionId`.
- Вспомогательная `actorRole(req)`: `sessionId` (кука/body) → `auth_session.user_id` → `user_account.role`. При отсутствии сессии/роли — `null`.
- Для защищённых эндпоинтов (`/api/users*`, `/api/seller/*/brands`) возвращать `403` при `null` или неверной роли.
- `configs/orders/settings` остаются на текущем уровне доверия `?userId` (демо) — серверно не защищаются в этой задаче.

Поскольку Админ/Продавец не имеют `phone`, SMS-вход для них не применим: form-таб «По телефону» остаётся, но при вводе телефона, совпадающего с известным аккаунтом admin/seller, сервер не связывает этот вход с ними (там нет phone) и не даёт их роли. Практически это означает: админ/продавец входят только через email-таб. Ограничение реализуется серверно (поиск по phone не возвращает админа/продавца) и на UI (подсказка войти по email).

### `src/screens/Profile.tsx`
- Бейдж роли: «Клиент» / «Продавец» / «Администратор».
- Отображение контактов: у Клиента — email и телефон; у Админа/Продавца — только email (телефон не показывать).
- **Редактирование аккаунта (Клиент и Продавец)**: поле «Имя» редактируется (клиент и продавец). Для Продавца — поле **«Компания»** редактируется. Изменения сохраняются через `PATCH /api/profile` (`updateProfile`); роль и контакты через этот экран не меняются.
- Продавцу: блок «Прайс-лист — в разработке» + список брендов из `GET /api/seller/:id/brands`.
- Админу: ссылка «Администрирование».

### Новый экран `src/screens/Admin.tsx` (роут `/admin`)
- Список пользователей, форма добавления (name, email, role; phone опционально; `company` для роли seller), удаление, смена роли (Select). Использует существующие UI-примитивы (Card, Table, Select, Button, Modal, hooks).
- **Правило контакта по роли**: при роли `customer` разрешён email и/или телефон; при роли `seller`/`admin` телефон не заполняется (хранится `NULL`), вход — только по email.
- Менять роль существующего пользователя: при переводе клиента в seller/admin телефон сбрасывается (`NULL`); при переводе в customer — телефон также сбрасывается (настраивается заново админом/пользователем), так как политика «телефон только у клиента».
- **Самообслуживание не через админку**: имя клиента/продавца и «Компания» продавца редактируются самими пользователями в `/profile`; админ может корректировать их при необходимости (через `PATCH` только для созданных/отредактированных полей при желании) — но основной путь — профиль.

## Риски / сложные места

- **Rebuild `user_account`** при изменении CHECK — самое рискованное. Корректно отключить/включить FK, отбросить гостевые строки, пересоздать связи/индексы, проверить `foreign_key_check`. `seed.js` тоже должен работать после миграции (или вызывать её).
- **Гость = аноним**: не создавать новую guest-запись в `Auth.tsx`; убрать все упоминания роли `'guest'` в коде (`auth.tsx`, `Profile.tsx`, `Navbar.tsx`, `api.ts`).
- **Порядок вставки в seed**: `seller_brand` вставлять ПОСЛЕ `user_account` (FK); после `DELETE` всех `user_account`.
- **Старые тесты/сессии**: тестовая БД пересоздаётся; убедиться, что проверки не зависят от гостевой сессии.
- **Ограничение вход по методу**: телефон доступен только клиентам. UI (`Auth.tsx`) и сервер (`POST /api/session`) не должны позволять админу/продавцу входить по SMS; при смене роли phone сбрасывается/не показывается.

## Оставшиеся вопросы (не блокируют)

- Размещение продавца: вкладка/секция в `Profile` (рекомендуется) vs отдельный роут `/seller`.
